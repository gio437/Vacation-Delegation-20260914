// Subscribes to the standard approval entry creation event. If the assigned
// approver has an active delegation for today, and the substitute is approved
// in this company, the entry is redirected before it is written. Every swap,
// and every swap refused, is logged.

[EventSubscriber(ObjectType::Codeunit, Codeunit::"Approvals Mgmt.",
  'OnBeforeApprovalEntryInsert', '', false, false)]
local procedure OnBeforeApprovalEntryInsert_SwapForVacationDelegation(
    var ApprovalEntry: Record "Approval Entry"; ...)
begin
    if ApprovalEntry."Approver ID" = '' then
        exit;

    // Already auto-approved (the approver is the submitter): leave it alone.
    if ApprovalEntry.Status = ApprovalEntry.Status::Approved then
        exit;

    OriginalApproverID := ApprovalEntry."Approver ID";

    // Resolves the substitute as of Today(), not WorkDate(), then confirms
    // they may approve in THIS company. If not, the approval stays put and
    // a Redirect Skipped entry records why.
    if not TryResolveSubstituteForThisCompany(ApprovalEntry,
        OriginalApproverID, SubstituteID,
        DelegationNo, HopsFollowed) then
        exit;

    ApprovalEntry."Approver ID" := SubstituteID;

    // Logged in the same transaction as the approval entry, so the log can
    // never claim a redirect that rolled back, or miss one that committed.
    DelegationLog.LogApprovalRedirect(
        ApprovalEntry, OriginalApproverID, SubstituteID,
        DelegationNo, HopsFollowed);
end;

Business Central has no way to say "I'm out until the 20th, send my approvals to someone else." This subscriber adds one.

Deployed in production across a 100-plus entity environment. Full writeup below. Also below: approval for vendor bank account changes.

Vacation Delegation for Business Central

When an approver goes on vacation, Business Central keeps routing approvals to them. Documents sit in the queue until they return, or an administrator reassigns each one by hand, or someone with SUPER rights approves it themselves. That last one is an internal controls problem, not just an inconvenience.

This extension lets a user register a substitute for a date range. Approval entries created for them during that range are redirected before they're written, and every redirection is logged with enough detail to answer an audit question.

Today() rather than WorkDate()

Business Central convention is to use WorkDate(). This extension deliberately doesn't.

During month-end close, finance users set their work date back into the prior period to post adjusting entries. If delegation keyed off WorkDate(), an approver working December's close in mid-January would have their January vacation evaluated against a December date, and the redirect would silently not fire.

Whether someone is on leave is a real-world calendar fact. It's not a posting-period question.

Delegation chains, with a cycle guard

If A delegates to B, and B is also out and has delegated to C, approvals for A should land on C. The resolver walks the chain, tracking visited users. If it encounters someone already visited, it stops and keeps the last resolvable substitute rather than looping. A hop limit of 10 is the second backstop.

while KeepResolving and (HopsFollowed < MaxDelegationHops()) do
    if not FindDirectSubstitute(CurrentUserID, ADate, ForCompanyName,
                                NextUserID, StepEntryNo) then
        KeepResolving := false
    else
        // Revisiting someone means a cycle (A to B to A). Stop and keep
        // whoever we last resolved to rather than looping forever.
        if VisitedUsers.Contains(NextUserID) then
            KeepResolving := false
        else begin
            if DelegationEntryNo = 0 then
                DelegationEntryNo := StepEntryNo;
            HopsFollowed += 1;
            VisitedUsers.Add(NextUserID);
            CurrentUserID := NextUserID;
        end;

The logged delegation entry is the first one in the chain, belonging to the original approver, because that's the entry that authorised diverting the approval away from them.

An empty control list blocks, it doesn't allow

Only users on an explicit approved list can be named as an approver or substitute. If that list is empty, the extension errors rather than letting anyone through.

if Approver.ListIsEmptyInCompany(CompanyToCheck) then
    Error('No approved delegation users are set up in company %1. ' +
          'An administrator must populate the Approved Delegation Users ' +
          'page there before delegations can be created.', CompanyToCheck);

The failure mode of a control list that fails to load should never be "no control." A misconfiguration stops work. It doesn't silently widen who can hold approval authority.

Partial rows can never redirect anything

Validation is tolerant of blank fields on write, so a field can be cleared and retyped, and a row only counts as active once every field is populated:

procedure IsActiveOnDate(ADate: Date): Boolean
begin
    exit(("Start Date" <> 0D) and
         ("End Date" <> 0D) and
         ("Substitute User ID" <> '') and
         (ADate >= "Start Date") and
         (ADate <= "End Date"));
end;

A half-entered row is simply never active, so it can't blank out an approval entry's approver.

The pages also insert a new delegation once, when the user leaves the row, rather than as soon as the first field is filled in. Without that, every following field was a separate save, and for an all-companies delegation each one wrote a log entry into every company. A save that changes nothing isn't logged at all.

No one approves their own request

A delegation mustn't become a way round segregation of duties. If the substitute it resolves to is the person who submitted the document, the redirect is refused: the approval stays with the original approver and the log records why.

if (SenderID <> '') and (SubstituteID = SenderID) then begin
    SkipReason := StrSubstNo(IsSenderLbl, SubstituteID);
    exit(false);
end;

The mirror case matters too. When the approver Business Central picks is the submitter, it creates the entry already approved. The subscriber leaves those alone, because putting the substitute's name on them would record someone approving a document they never saw.

Two different authority levels

The delegation table is self-service. You can manage delegations for your own approvals, and SUPER can act for anyone.

The approved-user list has no self-service case. Every write requires SUPER, and it's deliberately not exposed through the LOCAL permission set the rest of the feature rides on. That list decides who may hold delegated authority at all, which is a different question from who may use it. Changing the user on an existing row is a rename, which skips the normal modify checks, so renames are refused: replacing someone has to show in the log as one user removed and another added.

One delegation, every company, but each company still decides

Through version 2.0 a delegation was per company. An approver who approves in several entities had to enter the same delegation in each one, and missing one meant approvals quietly stalled there. Version 2.1 moves delegations into a single cross-company table. A delegation applies to all companies by default, or to one named company.

The risk is that a delegation entered in one legal entity could now hand approval authority to someone in another. So the approved-user list stays per company, and it's enforced at redirect time, in the company where the approval is actually being created:

if not SubstituteMayApproveInThisCompany(SubstituteID, SkipReason) then begin
    DelegationLog.LogRedirectSkipped(ApprovalEntry, OriginalApproverID,
        SubstituteID, DelegationNo, HopsFollowed, SkipReason);
    exit(false);
end;

If the substitute isn't on that company's list, is blocked there, or has no User Setup there, nothing is swapped. The approval stays with the original approver and the log records why. The approval request itself is never blocked.

Editing someone else's delegation that reaches outside the current company requires SUPER assigned for all companies. SUPER in one company shouldn't be able to reroute another company's approvals. And because the subscriber runs as whoever submitted the document, who may not hold LOCAL in that company, the reads and log inserts on the redirect path carry inherent permissions. A permission error there would block their approval request outright.

The audit log is append-only, and says so honestly

The permission set grants Read and Insert on the log table, not Read, Insert, Modify, Delete. No object in the extension modifies or deletes a log row.

The code comment doesn't overclaim: a SUPER user can still delete rows directly, because Business Central has no truly immutable storage. If the trail needs to stand up to an external audit, this is meant to be paired with the native Change Log on that table, or exported to an external archive on a schedule.

Changing a delegation is logged in every company its old scope covered as well as its new one, so narrowing an all-companies delegation to one company shows up in the companies it leaves.

Every redirect records the original approver, the substitute, how many hops were followed, which delegation authorised it, the document type and number, the amount, the requester, and the RecordId. The question an auditor asks is "who approved this instead of the person the workflow chose, and on what authority." The log answers both halves.

Populating the list without typing every name by hand

The control list can be built manually, one user at a time, but most of who should be on it is already sitting in Business Central's own approval configuration. A button on the approvers page runs PopulateFromApprovalSetup(), which pulls in anyone named as another user's Approver ID in User Setup, anyone carrying an approval limit or an unlimited-approval flag, and every member of a Workflow User Group.

It's a manual trigger, not a background sync. Someone presses the button when they want the list refreshed against current approval setup. It's also purely additive: it only adds users who aren't already on the list, so an admin who deliberately removed someone won't have them silently reappear the next time it runs.

Install and upgrade

Version 1 carried a hardcoded approver list. Version 2 moved it into a table. That creates a hazard: a tenant upgrading from 1 to 2 would land with an empty control list, and since empty blocks all writes, every delegation would break until an admin populated the page by hand.

Both an Install codeunit and an Upgrade codeunit seed the list, because upgrading fires OnUpgradePerCompany, not the install trigger. The seed only runs when the table is completely empty, so it can never overwrite a curated list.

Version 2.1 had a harder version of the same problem. Business Central won't switch an installed table from per-company to cross-company, so 2.1 adds a new table and migrates into it. Each company's rows are copied across as single-company delegations naming that company, so routing is exactly what it was before the upgrade, and nothing becomes cross-company until someone chooses it. Every move is logged, the migration is guarded by an upgrade tag so it's safe to re-run, and the old table is kept read-only so the move can be checked row for row.

What I'd do differently

The substitute's own approval limits aren't re-checked. Business Central picks an approver who is authorised for the amount, and this extension swaps the approver after that decision, so a substitute can receive an approval above their limit. Across companies their limits can differ too. The log records the amount, the requester and both approvers on every redirect, so it's detectable after the fact, but detection isn't prevention. Closing it is a controls decision as much as a code change, and it's documented as open rather than quietly left out.

ReassignOpenApprovalEntries() exists for entries created before a delegation was set up, or by batch jobs that don't fire the standard event. It's written but not surfaced on a page or scheduled.

There's no automated test suite. Testing was manual in a sandbox: create a delegation, submit a document, verify the entry lands on the substitute and the log row is written. Then chain cases, cycle cases, partial rows, expired ranges. The right answer is a test codeunit against the approval workflow test libraries, and that's the gap.

Vendor Bank Account Approval for Business Central

Changing a vendor's bank details is the classic payment-fraud move: one edit, and the next payment run sends real money to a new account. Business Central has approval workflows for vendors, customers and items, but nothing for the Vendor Bank Account table, so anyone who can edit the card can redirect payments.

This extension registers "A vendor bank account was changed" as a native workflow event and ships a ready-made workflow template, so approval is configured on the standard Workflows page rather than in custom code.

Hold until approved, not just flag

A status field that says "pending" while the new account number is already live isn't a control. The template uses Business Central's own Revert, Apply and Discard responses: the new value is stashed, the old one is put back, and it only goes live once the last approver signs off. Rejected changes are thrown away. Eight fields are protected, everything that decides where a payment goes: bank account number, IBAN, SWIFT, routing (transit) number, branch number, clearing code and standard, and the electronic payments flag.

It fails closed

If no enabled workflow picks a change up, the change is refused rather than saved silently. That's controlled by a Require Approval switch, on by default and gated behind its own permission set. Checking whether an approval request exists isn't enough, since a stale one from earlier would answer yes. So the subscriber counts what's held for approval before raising the event and again after, and refuses the save unless this change produced something new:

CapturedBefore := CountCapturedForApproval(Rec);

RecVariant := Rec;
WorkflowManagement.HandleEventWithxRec(
    RunWorkflowOnVBABankAccChangedCode(), RecVariant, StoredBefore);

CapturedAfter := CountCapturedForApproval(Rec);

if CapturedAfter <= CapturedBefore then
    if VBABankApprovalSetup.IsApprovalRequired() then
        Error(ApprovalRequiredErr);

New bank accounts go through the same path. Otherwise the obvious workaround is to delete the approved account and recreate it with different details, and nothing was ever "changed".

xRec can't be trusted

Before version 3.6.2, the subscriber compared Rec with xRec in OnAfterModifyEvent. That works for edits made on a page. For a modify made from AL code, such as an import, another extension or the extension's own dialog, xRec already holds the new values, so the change is invisible and never goes for approval. The fix reads the stored record from the database in OnBeforeModifyEvent, while it still holds the old values, and compares against that. It was found because the dialog runs its own independent fail-closed check, which refused the save.

One bank change, one approval

Business Central saves each field as you leave it. Editing the protected fields directly would raise a request on the first field and split one bank change across several approvals, with the record pairing a new account number with the old routing number in between. So the fields are read-only on the card, and a Change Bank Details dialog collects every new value and saves once. The approver sees each held change, old value to new, in Requests to Approve.

A second person, always

Business Central lets you approve your own request in two ways. If you're set up as your own approver, it creates the entry already approved, and an approval administrator can approve a request they sent themselves. For a change to where payments go, both are refused, and the error rolls the whole change back. An administrator can allow self-approval for single-user testing; it's off by default, including on setups that existed before the switch did.

if Rec."Sender ID" = Rec."Approver ID" then
    if not VBABankApprovalSetup.IsSelfApprovalAllowed() then
        Error(SelfApprovalErr, Rec."Sender ID");

Closing the engine's own back door

The subscriber has to let the workflow engine's own writes through: putting the old value back when a change is held, and writing the new one in once it's approved. It recognises them by matching the held old and new values. A review found that while a request was still open, any write that set a field to its proposed value looked exactly like the engine applying it, so the change went live early, and stayed live if the request was then rejected. Any other protected field changed in the same write went along with it.

Now a write only counts as the engine's when nothing is awaiting a decision, and only if every protected field it changed matches a held value.

An audit trail that doesn't depend on the extension

Installing or upgrading turns on Business Central's own Change Log for the protected fields, the approval status, and the vendor's preferred bank account. It only ever adds to existing Change Log settings. If the extension were ever removed or got round, the record of who changed which bank detail, from what to what, would still be there.

Deleting or renaming a bank account while a request is pending is refused too. Business Central tidies up requests when a vendor is deleted or renamed, but not a vendor bank account, so the request would be left stranded in the approver's queue.

What it still doesn't do

Nothing checks approval status at payment time. Deleting an approved account isn't blocked, and switching a vendor's preferred bank account to a different existing account needs no approval. Both now show up in the Change Log, but neither is gated, and they're documented as open rather than implied to be covered.

Findings from production

Most of what I do is finding where documented behaviour and actual behaviour diverge, usually because an extension or a batch process is overriding base Business Central. These are things I traced that weren't documented anywhere.

  • Fixed asset depreciation ignoring dimension priorities

    Configured Default Dimension Priorities for the FAGLJNL source code with G/L Account first and Fixed Asset second, so balance sheet lines would hold at the clearing department while P&L lines inherited the asset's operating department. It didn't work. The FA Posting Groups Allocation table had a department hardcoded, and it intercepts the batch before the dimension priority engine runs. Priorities were correct the whole time and never got a chance to execute.

  • Multi-entity payment routine ignoring native On Hold

    Invoices marked On Hold in the vendor ledger were still being pulled into payment batches. Native Suggest Vendor Payments respects the flag. The multi-entity extension's equivalent routine doesn't read it. Confirmed on fresh invoices with no applied entries, escalated to the vendor as a defect.

  • Version 27 upgrade impacts, traced after the fact

    Permission enforcement tightened and users lost access to tables that had previously been implicitly granted. The IRS 1099 single-code field was replaced with three fields. Source Currency Amount in G/L Entries started populating for local-currency transactions. Report timestamps stopped adjusting for daylight saving. None of these were in the release notes as user-facing changes. All surfaced as tickets.

  • Great Plains legacy conversion mapping

    Production GP to Business Central conversion was generating "not defined on Legacy G/L Conversion" errors for every new entity, division, and department combination, each needing a manual mapping row. Completed a project moving validation to default dimensions instead, which removed the recurring mapping work.

  • Sandbox copies blocking every page after refresh

    Every Copy to Sandbox operation threw a runtime error on nearly all pages. The cause was Business Central's own sandbox safety behaviour: outbound HTTP is blocked per extension by default, and the multi-entity extension calls a licensing endpoint on page load. The fix is a per-extension setting, not a re-copy. Documented as an SOP so the next refresh doesn't repeat the investigation.
